## Overview

Graph Paper Programming is lesson 2 of Code.org's CS Fundamentals Course D, an unplugged lesson
written for grades 3–5. Students "program" each other to fill in squares on a grid, using five
symbols. It introduces the difference between an **algorithm** (steps in everyday language) and a
**program** (the same steps encoded so a machine can follow them), and shows how exact a program has
to be. It also works as a quick, low-stakes start for older students who are new to programming.

## Preparing

- Print pages 1–3 for each group. Each program sheet (page 3) holds three programs, with space for
  the robot's drawing next to each one.
- Print page 4 for groups that finish early, and keep page 5, the answer key, for yourself.
- Have students cover or fold away page 2 when they swap, so the robot can't peek at the picture.

## Running the activity

1. **Warm up (10 minutes).** Ask: when do you need to follow steps in a set order? Then ask how a
   real robot, like a robot vacuum, knows what to do. Steer the discussion toward the idea that
   robots only follow their programming, using specific commands.
2. **Model it (10 minutes).** Be the robot. Show picture A on the board and have the class talk you
   through it in words, starting from the top-left square. Write each step down as you do it, then
   point out how long the list gets. Ask how symbols could make it shorter, and rewrite it with the
   five symbols. Words are the algorithm; symbols are the program.
3. **Program and swap (25 minutes).** In pairs or small groups, students choose a picture, plan it,
   write the program, and swap with another group. The robot follows the program exactly, even when
   it looks wrong. Groups then compare drawings, find bugs and fix them, then choose another
   picture.
4. **Wrap up (10 minutes).** Have students draw a picture of their own and write its program, or
   discuss the questions below.

## Things to watch for

- **The robot "fixing" mistakes.** Robots must follow the program exactly, not what they think it
  means. A bug that gets drawn is more useful than one that gets quietly corrected.
- **Filling before moving.** The robot starts on the top-left square, so a picture that starts
  with a filled corner begins with ■, not →. This is the most common bug.
- **Many right answers.** There is more than one correct program for every picture. The answer key
  gives one that reads the rows like a snake. If the robot draws the picture, the program works.
- **Writing layout.** Some students write programs left to right like a sentence; others start a
  new line for each row of the grid. Either is fine if the robot can follow it.

## Debrief

- What made a program easy or hard to follow?
- When the drawing was wrong, how did you find the bug: by reading the program, or by watching the
  robot?
- Why do computers need programs this exact, when people can understand "draw a smiley face"?
- The shorter-programs challenge uses numbers like 3→. What does that save, and where else do
  programs repeat the same steps? This leads into **loops**.

## Going further

- The shorter-programs challenge on page 4 previews loops. Have students find the program with the
  biggest saving.
- Change what the symbols mean: for a dance robot, → could mean "step right" and ■ "clap." What
  other robots could the class program?
- For a harder version, add a "pick up the pencil" and "put it down" symbol, so the robot draws
  lines instead of filling squares.
- [The original lesson](https://studio.code.org/courses/coursed-2022/units/1/lessons/2) has slides,
  a video of the lesson in action, and an optional assessment.
